# DX7 port notes

Port-specific findings for this plugin, moved here from mpc-vst-plugins' `docs/NOTES.md` (and its
`force-dx7-schwung` branch) on 2026-09-25, when that repo became port-generic. Paths such as
`force-dx7/vst-schwung/` are this repo's earlier location inside mpc-vst-plugins. Generic MPC plugin
facts stay in mpc-vst-plugins' `docs/NOTES.md`.

## Force DX7: pivot to schwung-dx7, standard pipeline, audio confirmed (2026-09-24)
Rebuilt the DX7 port from a different DSP source, at `force-dx7/vst-schwung/` (the control-socket
attempt above, `force-dx7/vst/`, is untouched -- both exist; a later session/user should pick one
to keep). Source: https://github.com/charlesvestal/schwung-dx7 (`main`, `86afe0062415b`), a real
Schwung `plugin_api_v2` module (Dexed/MSFA) exporting `move_plugin_init_v2` ->
`create_instance`/`destroy_instance`/`on_midi`/`set_param`/`get_param`/`get_error`/`render_block`
-- the same shape as Maze Voice, category 1 of docs/PORTING.md, not category 2. Cloned to
`.scratch/schwung-dx7` next to the worktree (gitignored, not vendored into this repo -- matches
how Maze Voice keeps its own DSP source in its own sibling repo, force-maze, rather than inside
mpc-vst-plugins).
- **module.json's own `chain_params` is NOT what this port uses.** schwung-dx7's `src/module.json`
  only lists ~20 "Move knobs" params (the curated UI subset), not chain_params at all (it uses a
  different `ui_hierarchy.levels.root.params` schema gen_vst.py doesn't read). Read
  `src/dsp/dx7_plugin.cpp`'s `v2_set_param`/`v2_get_param` directly instead (grepped every
  `strcmp(key, ...)` and the `opN_*` prefix handler) to build `force-dx7/vst-schwung/module.json`'s
  `chain_params` by hand (149 params, generated by a script, not committed) -- confirmed every key
  against the DSP's actual C++ source, not invented. This mirrors force-dx7's exact naming
  (algorithm, feedback, output_level, octave_transpose, per-op level/coarse/fine/detune/vel_sens/
  amp_mod/rate_scale/osc_mode, key_bp/ld/rd/lc/rc, 4-stage EG rates/levels, pitch EG, LFO) with one
  real semantic difference: **`opN_detune` is -7..+7 here** (schwung-dx7's `set_param` contract:
  `v = v + 7` before clamping 0..14 internally), not force-dx7's raw 0..14 -- noted in both
  module.json and layout.conf. No `mix.gain`/`mix.dest_idx` (force-dx7's routing knobs) -- Dexed
  has a single audio output, no per-voice mixer destination, so those were dropped, not renamed.
  BANKS tab dropped as expected (no static-VST-parameter analogue for a live bank/patch list);
  GLOBAL's readout/stepper `get=`/`idx=` widgets (force-dx7's live patch-name display, driven by
  its ctrl_sock) also dropped -- those pull live text over a control socket that doesn't exist for

- **Fixed a structural bug in `vst.json`'s own `build.root`/`sources`** found while doing the
  above: it pointed `root` at `.scratch/schwung-dx7` itself with sources+build path escaping back
  out to `force-dx7/vst-schwung/` via `../../`. That works for `gen_vst.py` (plain Python, no

  every other port's `root` is an ancestor of both the DSP source and the vst.json.
- **Real bank/patch capability, confirmed from schwung-dx7's actual API** (not force-dx7's design):
  `create_instance()` scans `<module_dir>/banks/*.syx` (33 shipped in this checkout: `Dexed_01.syx`

- **`layout.conf`'s GLOBAL tab now has a real bank/patch top bar**, recreating

### Real-device crash found by tools/bench.sh, fixed (2026-09-24, same day)
First real-device run of `tools/bench.sh force-dx7/vst-schwung/build/dx7_schwung.so <ip> -j`
(non-invasive, nothing installed) **segfaulted instantly, no bench output at all** -- not a
WARN/FAIL verdict, an actual crash. MPC itself was unaffected (confirmed still running afterward;
`bench.sh`'s own temp-file cleanup ran even after the crash).
- **Root cause, confirmed by reproducing it offline under ASan first**: `vst.json` never set
  `MODULE_DIR` (no `"defines"` block), so the built `.so` used `wrapper/vst2_wrap.c`'s bare
  default, `#define MODULE_DIR NULL`. schwung-dx7's `v2_create_instance()` does an unconditional
  `strncpy(inst->module_dir, module_dir, ...)` on that argument with no null check -- a literal
  NULL pointer segfaults there immediately, on the *very first* `create_instance()` call, i.e. the
  moment any host (bench.c's dlopen, or MPC's real plugin loader) opens the plugin at all. Built a
  host test that links the wrapper exactly as shipped (no manual `-DMODULE_DIR` override, unlike
  every earlier host test in this file, which had silently masked the bug by always overriding it)
  and got the identical ASan stack: `SEGV ... strncpy ... v2_create_instance
  dx7_plugin.cpp:634 ... VSTPluginMain vst2_wrap.c:276`. **No ASan-vs-device gap** -- it reproduces
  identically in-process; bench.c's dlopen path isn't structurally different here, the bug is a
  plain NULL dereference that any loader hits the same way.
- Everything downstream of that null check is already graceful by design and did NOT need fixing:
  `scan_syx_banks()`'s `opendir()` failure returns cleanly (`syx_bank_count = 0`), and
  `v2_load_syx()`'s `fopen()` failure also returns cleanly (logs, returns -1). The DSP's own
  built-in "Init" patch (set by `v2_init_default_patch()`, called unconditionally in
  `create_instance()` before any bank scan) is a real, audible patch on its own (algorithm 1, OP6
  as sole carrier at level 99) -- so "banks/ not found on this device yet" was already a safe,
  audible fallback; the ONLY actual crash path was the literal NULL argument.
- **Fix 1 (primary): `vst.json` now sets a real on-device `MODULE_DIR`**, `/sdcard/vst/
  dx7_schwung_banks` -- matching the existing convention in this repo for shipping extra runtime
  data next to a port's `.so` (`docs/RELEASING.md`'s `tools/release.py --extra SRC:vst/DEST`,
  which lands at `/sdcard/vst/DEST`, right beside `/sdcard/vst/x.so`). This is not yet deployed
  anywhere (no device install happened) -- when the user does install this port, they'll need to
  copy a `banks/` folder (schwung-dx7's own, or any `.syx` banks) to that path themselves as part
  of that step; until then the plugin still works (built-in Init patch), it just has nothing to
  browse.
- **Fix 2 (defensive, belt-and-suspenders): `wrapper/vst2_wrap.c`'s bare default changed from
  `NULL` to `""`** for any port that doesn't set `MODULE_DIR` at all, or (same effect) whose baked
  path doesn't exist on a given device. `""` is inert for a DSP that ignores `module_dir` entirely
  (Maze Voice), and safe for one that does `strncpy`/`snprintf` on it directly (schwung-dx7):
  `"%s/banks"` on `""` becomes `"/banks"`, `opendir()` fails cleanly (already-graceful path, see
  above), same Init-patch fallback. This is a shared-file change (affects every port that uses
  `module_dir`), justified because it's a plain crash-safety fix with no behavioural change for any
  port that doesn't dereference `module_dir`.
- **Retested, all green**: same ASan host test rebuilt using the port's own real generated
  `params.h` (now `MODULE_DIR="/sdcard/vst/dx7_schwung_banks"`, which doesn't exist on this x86
  box either) -- no crash, clean ASan, exit 0, and still non-zero audio (RMS 0.045, the built-in
  Init patch). Bank/patch switching retested with `MODULE_DIR` pointed at the local schwung-dx7
  checkout (temporary, uncommitted `params.h` override for this one offline test only) -- identical
  results to the earlier bank/patch retest (preset_next, next_syx_bank, absolute bank=5 all still
  produce different non-zero RMS with correct live bank/patch names), confirming Fix 2 didn't
  regress the feature.
- **Real-device bench, rerun after the fix: PASS.** `tools/bench.sh
  force-dx7/vst-schwung/build/dx7_schwung.so 192.168.1.44 -j`:

  | Stage | mean% | p99% | max% | threads% |

  | idle | 0.1 | 0.2 | 0.5 | 0.0 |
  | 1 voice | 0.2 | 0.4 | 0.7 | 0.0 |
  | 4 voices | 0.4 | 0.8 | 1.0 | 0.0 |

### First real interactive device test: "click"/no sound, bank+knob unresponsive (2026-09-24)
After the rename to `force-dx7/vst-schwung/` -> "DX7 (Dexed)" (`.so` `dx7_dexed.so`, banks dir
`/sdcard/vst/dx7_carts`, `MPC.settings` updated and `acvs` restarted -- all done directly by the
user/coordinator over SSH, not by this session), the user's first real interactive test reported:
bank/preset stepper and a knob unresponsive, stuck on the Init patch, and no sound ("or maybe a
kind of click"). This was the first-ever real MPC-host interaction with this port -- everything
before this was `tools/bench.sh` (CPU-cost playback only, no UI/param interaction) or this
session's own synthetic `host_test.c`-style ASan harnesses.

**Confirmed and fixed, with concrete evidence:**
- **`/sdcard/vst/dx7_carts` contains real, intentional mixed content** the user placed there on
  purpose (confirmed by the user directly) and wants to keep using: `Dexed_01.syx` (this port's
  own factory bank), 32 named carts, a `Legowelt magic DX7 cart.syx`, `readme.txt` (not a bank),
  and `hypra-rom.syx` at 131328 bytes -- **exactly 32 x 4104**, a ROM cartridge dump of 32 banks
  concatenated back-to-back, not one oversized/malformed bank. schwung-dx7's scanner only ever
  understood one bank per file (`if (size != 4104) return -1`); it would have listed
  `hypra-rom.syx` as a "bank" but failed to load it every time (size check), and `readme.txt` was
  already correctly skipped by its `.syx`-only extension filter. **Rewrote
  `scan_syx_banks()`/`v2_load_syx()`** (in the vendored `.scratch/schwung-dx7` checkout -- see the
  vendoring caveat below) to parse N back-to-back 4104-byte banks per file: any `.syx` file whose
  size is an exact multiple of 4104 is expanded into that many browsable `syx_banks[]` entries
  (`sub_index` added to `syx_bank_entry_t`; `v2_load_syx()` now takes a `sub_index` and reads only
  that 4104-byte slice via `fseek`). Multi-bank files get a disambiguating display suffix,
  e.g. `hypra-rom [3/32]`; `get_param("bank_name")` now returns the scanned list entry's own name
  directly instead of re-deriving from `patch_path` (which couldn't distinguish sub-banks of the
  same file). A file whose size ISN'T an exact multiple of 4104 (truly corrupt/unrelated) is
  skipped with a log line, never added as a broken entry.
  - Verified offline against a **local reconstruction of the real directory** (not the live device
    path -- copied its exact file-type mix instead per the hard stop): a real 4104-byte bank, a
    `readme.txt`, a synthetic 131328-byte "ROM" file built by concatenating a real bank 32 times
    (real DX7 sysex content, not padding), and a genuinely corrupt 5000-byte file. Result: the
    corrupt file and `readme.txt` never appear as a browsable bank; the ROM file's all 32 sub-banks
    are reachable via `next_syx_bank`/absolute `syx_bank_index` and are individually distinguishable
    (`hypra-rom [1/32]` .. `[32/32]`); every bank hop stayed audible; clean ASan run, no crash, no
    leaks. Also re-ran the pre-existing bank/patch and crash-safety host tests against the real
    schwung-dx7 checkout (33 single-bank files) and the no-`MODULE_DIR` scenario -- both still pass
    identically, no regression.
  - **Also fixed `syx_bank_index`'s own VST param range**: it was `min=0 max=32` (a leftover from
    when I only had 33 total banks to test with), which would have silently capped the achievable
    on-device range to the first 33 scanned entries even after this fix -- with the real mixed
    content now expanding to ~65+ entries (1 + 32 named carts + 1 + 32 hypra-rom sub-banks), that
    cap was a real, separate bug. Raised to `max=998` (`MAX_SYX_BANKS-1`).
- **Confirmed, by diffing the rename commit (`d216691`) directly, that it did NOT touch
  `chain_params`** -- only `id`/`name` (module.json), `name`/`so`/`MODULE_DIR` (vst.json), and a
  comment (layout.conf). Every parameter's VST index is provably unchanged by the rename.
- **Confirmed, by inspecting the actual generated `TUI.json`**, that on-screen knob bindings are
  correct at the JSON level: `PRESET`'s `Data` handle maps to `Parameter 0` (chain_params index 0,
  `preset`), `ALGORITHM` maps to `Parameter 4` (`algorithm`) -- exactly matching module.json's
  array order. If the currently-installed skin is this exact freshly-rebuilt artifact, the
  knob-to-parameter wiring itself is not the bug.
- **Added one defensive hardening to the shared wrapper**: `e->process` (the legacy, non-replacing
  VST2 opcode) was left as a null function pointer -- any host that called it instead of
  `processReplacing` would crash outright. Implemented a real accumulating `process()` (adds into
  the existing buffer, per VST2 spec, not an overwrite) and wired it in. This is defensive, not a
  confirmed cause: every host tested against this codebase (MPC's JUCE included, per the shared
  `wrapper/vst2_wrap.c`'s existing real-device track record with Maze Voice) sets
  `effFlagsCanReplacing` and is expected to always prefer `processReplacing`.

**Investigated, could NOT reproduce or confirm offline -- says so plainly rather than guessing:**

Q-Links and audio are independently verified working on real hardware (extensively, elsewhere in

### RESOLVED: the actual root cause was scan_syx_banks()'s hardcoded "/banks" suffix (2026-09-24)
The coordinator found and fixed it directly (deployed to the device, `dx7_dexed.so` md5
`9293372b25054db1d1cbac8b818efcb1`), confirmed identically reproducible in this session's own
rebuild of the same patched source. Root cause: `scan_syx_banks()` always did
`snprintf(dir_path, sizeof(dir_path), "%s/banks", inst->module_dir)` -- stock schwung-dx7's Move
convention, where `module_dir` is a parent folder that itself contains a `banks/` subfolder. This
port's `vst.json` sets `MODULE_DIR` directly to the cart folder itself
(`/sdcard/vst/dx7_carts`), which has **no nested `dx7_carts/banks/`** -- so `opendir()` failed
silently on every real device load, `syx_bank_count` stayed 0, and the plugin permanently fell
back to the built-in Init patch. This is exactly the reported symptom (stuck on Init, bank/preset
stepper and the knob do nothing) and had nothing to do with the mixed-content directory, the
rename, or the VST2 wrapper -- `scan_syx_banks()` was failing before it ever got far enough to
list `readme.txt`/`hypra-rom.syx`/anything else. **My own earlier local test fixtures had
independently masked this exact bug**: I always built a nested `<test_dir>/banks/` subfolder to
match stock schwung-dx7's convention (matching how the *upstream* checkout is laid out, e.g. this
session's own `.scratch/schwung-dx7/banks/`), never testing the flat, no-nested-`banks/`
directory this port's `vst.json` actually configures on a real device. Re-ran every offline test
in this file's history against the corrected flat convention (`MODULE_DIR` pointing straight at a
folder of `.syx` files, no `banks/` subfolder) after pulling in the fix: crash-safety, bank/patch
stepping against the real schwung-dx7 factory banks, and the mixed-content (readme/corrupt/ROM
dump) scenario -- all still pass, clean ASan, no regressions, and `tools/build_port.sh`'s armhf
output reproduces the coordinator's exact deployed md5 byte-for-byte.

Whether this also explains "no sound" (as opposed to "stuck on Init, which is itself audible per
the DSP's real default patch") is still open -- the user hadn't retested as of this note. If sound
is now working too, the "no sound even with the real Init patch" thread from the previous entry
was a red herring caused by never getting bank-scan-related state right at all (a bank-scan
failure doesn't itself silence a plugin -- the Init patch is genuinely audible -- so if this alone
fixed everything, the "no sound" report was likely just consistent user-facing symptoms of the
same underlying stuck-on-Init state, not two separate bugs). If sound is STILL silent after this,
that's confirmation the audio-path investigation from the previous entry remains a live, separate

### RESOLVED: bank_name/patch_name readouts never refreshed -- same fix as jv880's (2026-09-25)
Confirmed the user's own read on this ("similar problem to what we solved on jv880") was exactly
right. Traced `v2_get_param()`'s `"bank_name"`/`"patch_name"` handling and where the backing
fields get written (`inst->patch_name` -- `v2_select_preset()` line ~639, called from both
`set_syx_bank_index()` after a bank load and directly from `set_param("preset", ...)`;
`bank_name`'s own get_param returns the scanned `syx_banks[]` entry's name directly, no cached
copy at all): **the DSP side was never the bug.** `get_param("patch_name")`/`get_param("bank_name")`
had already been proven returning correctly-updated text across a bank/preset change in this
file's own earlier entries (e.g. `"Say Again."` -> `"PIANO   3 "` after `next_syx_bank`) --
re-confirmed again this session with a new permanent regression test
(`host_test_readout_update.c`, see below) before touching anything, specifically to rule the DSP
in or out before looking elsewhere.

The actual bug was on mpc-vst's own `main` branch already, just not yet on this branch:
`wrapper/vst2_wrap.c` never called `audioMasterUpdateDisplay` (VST2 opcode 42). A `stepper`'s
`get=`-bound readout is a *separate* Q-Link/param (`syx_bank_index`/`preset`) reporting its own
normalized value, which for a `min==max` degenerate string-only param never itself changes value
-- so MPC has no signal telling it to re-poll that param's *displayed text* just because a
DIFFERENT param (the stepper's real target) changed it indirectly. `main` had already found and
fixed this exact issue for jv880 (commit `8b69732`, "Defer audioMasterUpdateDisplay to
processReplacing"); this branch had diverged before that commit landed, so it needed porting in
by hand rather than a straight merge (this branch had also independently added a `process()`
implementation in the meantime, touching the same render path). Ported: `need_update_display`
flag set by `setParameter()` (both the `step_target` branch -- `next_syx_bank`, `preset_next`,
etc. -- and a plain direct param set, matching jv880's fix exactly, since a raw Q-Link turn on the
target param needs the same signal), consumed once per audio block from a renamed
`run_deferred_host_callbacks()` (was `run_release_callbacks()`, now also drains
`need_update_display`) called from both `processReplacing()` and `process()`.

**New permanent regression test**: `host_test_readout_update.c` -- a fake host callback counts
`audioMasterUpdateDisplay` (opcode 42) calls. Verifies, against the real schwung-dx7 factory
banks (flat `MODULE_DIR` convention): (1) `patch_name` actually changes text after
`preset_next` (`'Say Again.'` -> `'LAURIE    '`) with exactly one deferred `UpdateDisplay` call
drained on the next block; (2) `bank_name` actually changes (`'Dexed_01'` -> `'SynprezFM_01'`)
with the same one-call pattern; (3) a plain unrelated param set (Algorithm) also triggers exactly
one deferred call, matching jv880's fix (both a stepper-arrow tap and a direct Q-Link turn need
the signal); (4) an idle block with nothing changed triggers zero calls (no spurious host
re-entry). All four PASS. Also reran the full existing suite (crash-safety, bank/patch stepping,
mixed-content ROM-dump scenario) against the merged wrapper -- no regressions, clean ASan
throughout. `tools/build_port.sh`'s armhf rebuild: `dx7_dexed.so` md5
`5b0d5b9134421d7dc239a48b092fb4e7` -- not yet deployed by the coordinator as of this note.

This is the **second** time a bank/patch readout issue has surfaced (jv880, then this port) --
worth calling out explicitly since `host_test_readout_update.c`'s pattern (a fake host counting
`audioMasterUpdateDisplay` calls) is cheap and generic enough that any future `stepper`/`readout`
`get=`-bound port could reuse the same shape of test before ever reaching a real device.

## Force DX7: engine-with-host-side-glue port, audio bridge left open (2026-09-24)
**RETIRED (2026-09-24), superseded by `force-dx7/vst-schwung/`** (see the pivot section below):
the user decided to keep the schwung-dx7-based port, which produces real audio, instead of this
one, which never did. Kept here for the lesson learned (a standalone-process/control-socket/
shared-memory engine does not fit a VST's `processReplacing` call without real audio-bridge work);
`force-dx7/vst/`'s files themselves are left in place pending the user's own removal (not deleted
by an agent -- destructive repo deletions need the user's direct go-ahead, not a relayed one).
Ported force-dx7 (a standalone `dx7_host` process wrapping Dexed/MSFA, controlled over a
Unix control socket -- see `force-dx7/src/dx7_host.cpp`) to `force-dx7/vst/` in this repo.
Not built through `tools/build_port.sh`/`wrapper/vst2_wrap.c` (no directly-linkable DSP
module here, category 2 of docs/PORTING.md): a port-specific wrapper, `force-dx7/vst/
dx7_vst.c`, plus its own `build.sh`, `gen_params.py`, `params.json` (152 params, hand-derived

Force page/VST would want) and `layout.conf` (theme + GLOBAL/OP1-6 tabs copied from

- **Params, MIDI, chunk save/restore: wired and offline-tested.** The wrapper spawns
  dx7_host via `posix_spawn` (LD_PRELOAD stripped) if none is reachable at its control
  socket, else attaches to the one already running (matches the device's real model: one
  shared dx7_host, started from /moduler, not one per plugin instance). Every param get/set

  documented single-producer/single-consumer, with ForceAudioJack.so as the sole consumer

  opens as sole owner -- a small, additive change to `force-dx7/src/dx7_host.cpp`, no risk to
  the existing shadow-GUI path. Until then this port is a remote-control + MIDI-conduit
  plugin for whichever dx7_host is running; actual sound still reaches speakers only via
  ForceAudioJack, exactly as today's shadow-GUI addon.
